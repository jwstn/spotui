Lesson 09 / about 10 minutes

Choose where request data becomes trusted.

The response schema belongs to the caller. The request boundary needs a similarly deliberate decision.

Win for this lesson: You will be able to distinguish encoded request data from decoded internal request values and choose where schema decoding belongs.

1. Two representations

RepresentationExampleTrust level
Encoded inputurl: "https://api.spotify.com/v1/me"External or boundary data; needs validation and decoding.
Decoded valueurl: new URL(...)Internal value that already passed the URL schema.

The current file uses Schema.URL, whose type is a URL object, while callers pass strings. The schema describes a decoded value, but the boundary receives encoded data.

2. Decode strings with the right schema

The effect-smol schema reference distinguishes Schema.URL from Schema.URLFromString:

const CurlRequestSchema = Schema.Struct({
  method: Schema.Literals(["GET", "POST"]),
  url: Schema.URLFromString,
  headers: Schema.Record(Schema.String, Schema.String),
  form: Schema.optional(Schema.Record(Schema.String, Schema.String))
})

Decoding this schema can turn a caller-friendly string into the internal URL value. The key is not the particular schema name; it is matching the schema's encoded input to the data the boundary actually receives.

3. Where should decoding happen?

There are two reasonable designs:

Design A: service accepts encoded request
caller -> CurlService.runJson(schema, encodedRequest)
       -> CurlService decodes request and response

Design B: service accepts decoded request
caller -> decode request once
       -> CurlService.runJson(schema, decodedRequest)

For this application, the request builders are internal and already centralized. Design B can keep the service contract narrower, while Design A is useful if requests arrive from an untrusted boundary. Choose based on where the data enters the system, not on which schema looks more impressive.

4. Interface consequence

If the service accepts decoded requests, its contract can avoid leaking schema decoding requirements for the request:

runJson<S>(
  schema: S,
  request: DecodedCurlRequest
): Effect<S["Type"], CurlError | SchemaError, S["DecodingServices"]>

If the service accepts encoded requests, request decoding becomes part of its own error and environment contract. Both are valid. The mistake is leaving the representation implicit.
