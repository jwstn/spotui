Lesson 04 / about 8 minutes

An error is retained data.

Design error fields for the moment after failure, when the error may be logged, displayed, nested as a cause, or held in application state.

Win for this lesson: You will be able to distinguish useful diagnostics from secrets and raw provider data that should never enter a retained error.

1. Why full args are unsafe

The current CurlProcessError stores args. But curl arguments include:

--header "Authorization: Bearer <access token>"
--data "refresh_token=<refresh token>"

Once those values enter an error, they may be retained by a higher-level error, printed by a logger, shown in a crash report, or inspected during debugging.

2. Store a safe request summary

Prefer a deliberately small summary:

request: {
  method: "POST",
  host: "accounts.spotify.com",
  path: "/api/token"
}
statusCode: 401
exitCode: 22
kind: "http"
retryAfterSeconds: null

Do not store raw command arguments, authorization headers, form values, query strings that may contain credentials, or unrestricted response bodies.

3. Redacted is helpful, not magic

The effect-smol Redacted reference says that normal string, JSON, and inspection output hides the wrapped value. It reduces accidental leaks:

const token = Redacted.make(accessToken)
// logs and inspection show a redacted placeholder
const raw = Redacted.value(token) // trusted code can recover it

It is not cryptographic protection. The underlying value remains in memory. More importantly, redacting a credential in one object does not make it safe to place the original credential into curl arguments or another error field.

4. Error type as an interface

A typed error does two jobs:

  • It gives program code stable fields such as kind and statusCode.
  • It defines what diagnostic data the application is allowed to retain.

That means the error schema is part of the service interface, not an afterthought added when logging fails.
