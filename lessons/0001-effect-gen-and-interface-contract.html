Lesson 01 / about 8 minutes

Effects are values. Interfaces are contracts.

Use one distinction to understand the first bug in attempt and the first rule of solid Effect service design.

Win for this lesson: You will be able to predict whether an Effect function returns the response you intended or accidentally returns another Effect.

1. The contract

Read an Effect type as a three-part contract:

Effect<A, E, R>
          |  |  |
          |  |  required environment
          |  possible failure
          successful value

For a curl boundary, the useful target is something like:

attempt(request): Effect<CurlResponse, CurlError, never>

The caller should receive a response or a typed error. It should not need to know whether the implementation uses curl, fetch, or a fake process runner.

2. The current bug

In src/service/curl.ts, attempt is written as an Effect generator:

const attempt = Effect.fn("CurlService/attempt")((request: CurlRequest) => {
  return Effect.gen(function* () {
    const args = yield* buildCurlArgs(request)
    return Effect.timeoutOrElse(runProcess(args), {
      duration: "15 seconds",
      orElse: () => Effect.fail(timeoutError)
    })
  })
})

The expression after return is an Effect value. The generator does not run it. Therefore the generator succeeds with that Effect as its value:

Effect<Effect<ProcessResult, CurlProcessError>, never, never>

That is a nested Effect. It is usually a design smell at this boundary because the public method promised one operation, not an operation that hands the caller another operation.

3. Yield versus return

ExpressionWhat happens
return 42The generator succeeds with the number 42.
return Effect.succeed(42)The generator succeeds with an Effect object. The result is nested.
return yield* Effect.succeed(42)The Effect runs and the generator succeeds with the number 42.

So the local correction is conceptually:

return yield* Effect.timeoutOrElse(runProcess(args), options)

Do not patch the file yet. First learn to recognize the contract that the interface should enforce.

4. What Effect.fn adds

The effect-smol reference describes Effect.fn("Name") as a reusable function builder with a readable tracing and stack-frame boundary.

const attempt = Effect.fn("CurlService.attempt")(
  function*(request: CurlRequest): Effect.fn.Return<CurlResponse, CurlError> {
    const args = yield* buildCurlArgs(request)
    return yield* Effect.timeoutOrElse(runProcess(args), options)
  }
)

Notice two design choices:

  • The generator body makes sequencing visible.
  • The return annotation states the intended boundary and lets TypeScript expose accidental nesting.

Use Effect.fnUntraced for reusable helpers where tracing is not useful. Use the named Effect.fn form for important service operations such as an attempt, request, or decode step.

5. Interface lens

attempt is an implementation step, not necessarily the public service interface. A stronger design will later separate:

request model
  -> process execution
  -> response classification
  -> JSON decoding
  -> Spotify domain mapping

Each seam can then state one focused guarantee. The Spotify API should not receive a raw process result, and the process runner should not know Spotify schemas.
