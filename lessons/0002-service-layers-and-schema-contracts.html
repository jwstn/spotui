Lesson 02 / about 10 minutes

Put each promise at the right boundary.

Keep Bun concrete when that is the real runtime decision, while still making the curl service's semantic contract small and typed.

Win for this lesson: You will be able to explain why the curl transport should decode a caller-supplied schema without knowing Spotify's domain types.

1. Do not abstract imaginary variation

An interface is not automatically better because it hides an implementation. It earns its place when it hides a meaningful policy, protects an invariant, or gives tests control over a real boundary.

Your decision to keep Bun concrete is reasonable:

  • Bun is the committed runtime.
  • A runtime migration is not a current requirement.
  • Child-process behavior can be covered by live tests.

The important distinction is this: R = never means the Effect Context has no required service. It does not mean the operation is pure or has no operating-system behavior.

2. Service contract versus implementation

The effect-smol service example separates a service's contract from the layer that constructs it:

class CurlService extends Context.Service<CurlService, Interface>()(
  "SpotUI/CurlService"
) {}

const CurlServiceLive = Layer.effect(
  CurlService,
  Effect.gen(function* () {
    // build the concrete implementation here
    return CurlService.of({ runJson })
  })
)

The service says what callers may use. The layer says how the application supplies it. This lets callers depend on CurlService without knowing whether the implementation uses Bun, curl, or a test implementation.

3. Who owns the response schema?

Spotify's auth module knows the token response shape. Spotify's library module knows playlist and track shapes. The curl service should know none of those fields.

AuthService
  - owns RawTokenResponseSchema
  - asks CurlService to decode it

CurlService
  - owns process execution
  - owns status classification
  - owns JSON parsing
  - performs decoding using the supplied schema

The contract can be conceptually expressed as:

runJson(schema, request)
  -> Effect<Schema.Type<typeof schema>, CurlError | SchemaError, ...>

The exact generic spelling is version-sensitive, but the design is stable: the caller supplies the schema, and the transport service supplies the decoding machinery.

4. Input schema and output schema are different jobs

SchemaOwnerPurpose
Request schemaTransport boundaryTurn external request data such as URL strings and header records into trusted internal request values.
Response schemaCaller or domain moduleTurn an unknown JSON response into the shape that caller actually understands.

The current file declares Schema.URL and Schema.Headers as types but never decodes with them. That creates the appearance of validation without the behavior. The effect-smol schema reference describes Schema.decodeUnknownEffect as the boundary that turns unknown input into a typed Effect failure.

5. The composition

const runJson = Effect.fn("CurlService.runJson")(
  function* (schema, request) {
    const response = yield* attempt(request)
    const json = yield* parseJson(response.body)
    return yield* Schema.decodeUnknownEffect(schema)(json)
  }
)

Each yield* adds the called operation's failures to the enclosing contract. The curl service does not need to know whether the schema describes a token, playlist, or track.
