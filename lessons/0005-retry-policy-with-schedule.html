Lesson 05 / about 10 minutes

Retry policy belongs in structured errors.

Use Effect's retry machinery without turning messages into an accidental protocol.

Win for this lesson: You will be able to explain why HTTP failures must enter the error channel before Effect.retry can handle them.

1. Retry only sees failures

Effect.retry retries when an Effect fails according to a Schedule. It does not inspect a successful value looking for an HTTP status.

request
  -> process exits with HTTP 503
  -> classify as CurlProcessError(kind: "http")
  -> Effect.retry sees the error
  -> schedule decides whether to try again

If a 503 response is returned as a successful CurlResponse, the retry policy cannot see it. This is why status classification belongs inside the curl transport boundary.

2. Structured policy beats message matching

type RetryableCurlError = {
  kind: "process" | "timeout" | "http"
  statusCode: number | null
  retryAfterSeconds: number | null
}

const isRetryable = (error: RetryableCurlError) =>
  error.kind === "process" ||
  error.kind === "timeout" ||
  (error.statusCode !== null && error.statusCode >= 500) ||
  error.statusCode === 429

Do not write policy such as message.includes("timed out"). Messages are for people and may change. Tags and fields are for program behavior.

3. Build a schedule

The effect-smol schedule example combines a backoff with a retryability predicate:

const retrySchedule = Schedule.exponential("300 millis").pipe(
  Schedule.jittered,
  Schedule.setInputType<CurlProcessError>(),
  Schedule.while(({ input }) => isRetryable(input))
)

const run = attempt(request).pipe(
  Effect.retry(retrySchedule)
)

The schedule controls timing and continuation. The typed error controls whether continuation is allowed. A bounded retry count should also be part of the policy.

4. Retry-After is data, not decoration

A server may provide a retry delay. If the error stores retryAfterSeconds but the schedule ignores it, the interface contains policy data that the implementation does not honor.

That is a design smell: either make the schedule use the field, or do not claim that the field represents the active retry policy. We will handle dynamic delays after the basic retry contract is clear.
